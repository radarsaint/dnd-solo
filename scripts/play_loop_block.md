## During play: run the commands, never read the runtime (hard rule)

- **Per-turn contract: [docs/PLAY_CARD.md](docs/PLAY_CARD.md).** Read it once at mount (it is also `play_card` on the opening packet). Do not reread repo docs, the runtime, or a log during play. One player message is one prepare and one complete. A rejection's `Fix:` line is the only edit; complete that same `turn_id` once. A committed roll_call, clarify, risk_confirm, or reaction is a complete turn: show `spoken` and stop.
- **Never open, search, or inspect runtime source, schemas, or tests during play.** The packet tells you everything a turn needs. If something is unclear, follow the packet's instructions or `retry_instruction`, or run `rehydrate`. Each command takes about 0.1 s; slow turns come from reading code.
- **Per turn, exactly this:**
  1. Write the player's exact words to `a.txt`, then run `python3 -m runtime.kit_agent prepare --one-pass --db kit.sqlite --action-file a.txt`
  2. Write one JSON object `{"decision", "performance", "manifest"}` to `o.json`, following the packet. `manifest` is only `{"session": "<hash>", "room": "<hash>"}`. Copy filled examples from `shapes`.
  3. Run `python3 -m runtime.kit_agent complete --db kit.sqlite --turn-id <turn_id> --input-file o.json`. If accepted, show only `spoken`. If rejected, paste `fix` and complete the same `turn_id` once. Do not prepare again.
- **Turn spine:** the packet's `player_move` and `open_ask` say what the player did and what Kit is waiting on. Answer the open ask first (a number inside a question still answers it), keep the PC where the player said he is, and ask or resolve in a reply, never both. Details: PLAY_CARD "Moves and open asks".
- **If `prepare` returns `turn_pending`:** a turn is already waiting and nothing was recorded. Run its `next_command` (the `complete` for that `turn_id`). A bare yes completes the pending opening: prepare returns `spoken` and you show it. It is never an in-fiction action. Do not draft a decision for it.
- **Time caps (hard rule):** never work silently. Setup (mount through the ready line) has a 3-minute total cap and a turn has a 90-second cap. When a step runs past its cap, stop it and tell the player in one line what you were doing (for example `Still reading the opening scene; one more try.`), then continue or ask. During setup, post a one-line progress note at least every 60 seconds. Say the landing `table_line` right after `adventure prepare` returns, and do the skim while the player answers.
- **Hand-resolved beat (record it):** when you rule a beat yourself instead of completing the prepared turn (a fight breaks out, creatures reveal themselves), record it before the next turn so the engine agrees with the table: `python3 -m runtime.kit_agent record --db <db> --input-file beat.json` with `{"happened": "...", "revealed": ["names or creatures now known"], "facts": ["..."], "encounter": "started" | "ended" | null}`. It drops the prepared turn; revealed names leave the spoiler fence; an encounter flag makes later rules questions answer for that fight. It runs no combat. Never name host tools, files or fields to the player ("roll it and tell me the total").
- **Adventures:** `start` lists playable modules in `modules_available`. If the player supplies an adventure PDF, run `python3 -m runtime.kit_agent adventure prepare <file> --db kit.sqlite` (one step, about 2 seconds: ingest plus the full structural index, cached per book so the same book never prepares twice), then say its `table_line` to the player at once. If it reports `cached: true` with `skim_status: accepted`, the opening is already done: run `status` and start. Otherwise skim only the opening pages and run `python3 -m runtime.kit_agent adventure skim --db kit.sqlite --file skim.json` with one JSON object (`burst`, `source_quote`, `page_start`, `page_end`, `alt_starts`, `design_start_name`, `scene`). **For a PDF, `scene` is mandatory:** use the private host-only excerpt to interpret who is physically in this encounter, what they want, what can be found, and what pressure is possible. Give each claim its whole source sentence and `established`, `conditional`, or `inferred` evidence status. Do not add DCs, surprise, attack outcomes or characters named only in setup. Python validates. Do not label the book to find the opening. On `scene_required`, **do not start or show the source excerpt to the player**: the host fills `scene_request` using the supplied private `source_span`, writes `{"scene": ...}` to `skim.json`, and repeats `skim_command` in the same exchange. Correct any named field errors; this is a repair, never a picker. `scene_verified` must be true before Yes. starts a PDF. On a pass, a bare Yes. speaks the burst. A genuinely invalid opening quote (not a scene-form error) offers the picker; do not open a later room. Then run `python3 -m runtime.kit_agent status --db kit.sqlite` and, when the player says begin, run its `next_command`. Never trigger full indexing from Yes., Go on, or a player action; if indexing fails, report preparation incomplete and retry the preparation command instead of inventing later rooms. Pasted text: save it as `adventure.txt` (page breaks as form feeds; boxed read-aloud lines keep the `> ` prefix) and run `python3 -m runtime.kit_agent adventure import --db kit.sqlite --text-file adventure.txt`, then the same skim. A PDF with no text layer is refused in one line; ask them to paste the text. If `pdfplumber` is installed (`python3 -m pip install -r requirements.txt`), it reads the PDF's columns and boxes first; otherwise the built-in reader does. `pdftotext -layout` or `pypdf` run only if those cannot read the text layer. Locations after the first compile themselves on arrival. If import refuses, say in one line what is missing. Never build rooms, NPCs, stat blocks, or a module yourself, and never edit compiled rooms.
- **Party companions:** not supported yet. (Planned: Kit plays a party member from that member's own sheet, without her DM knowledge.) Say so in one line. Never fake a companion, and never size the party or encounters to a published adventure's party. The party is the player's own character(s).
